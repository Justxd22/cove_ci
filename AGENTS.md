The role of this file is to describe common mistakes and confusion points that agents might encounter as they work in this project. If you ever encounter something in the project that surprises you, please alert the developer working with you and indicate that this is the case in the AGENTS.md file to help prevent future agents from having the same issue.

- Use `cove_util::ResultExt::map_err_str` instead of `.map_err(|e| Error::Variant(e.to_string()))` — it's cleaner and equivalent
- Use `cove_util::ResultExt::map_err_prefix` instead of `.map_err(|e| Error::Variant(format!("context: {e}")))` when the prefix is a static string — produces `"context: error_message"`
- For long-lived UI-facing managers, prefer `dispatch(action:)` for user intents and keep named methods for reads, bootstrap/lifecycle hooks, and special service-style operations.
- For long-lived UI-facing managers, use `state()` for the initial snapshot only. Ongoing UI updates should use typed delta reconcile messages for fields/events instead of re-sending the whole state after every mutation
- never use `pub(in ...)` or `pub(super)`; if non-private visibility is needed, use `pub(crate)` or `pub`
- never manually edit generated files
- no mod.rs files use the other format module_name.rs module_name/new_module.rs
- adding `arti-client` naively currently causes a Cargo links conflict: Arti pulls `tor-dirmgr -> rusqlite 0.38 -> libsqlite3-sys 0.36` while Cove already uses `rusqlite 0.31 -> libsqlite3-sys 0.28`; Cargo rejects having two crates with `links = "sqlite3"` in the same final graph
- surprise/confusion point: `just run-android` (`xtask run-android`) only does Gradle assemble/install/launch for the dev APK and does not rebuild Rust JNI libs or regenerate UniFFI Kotlin bindings. For Rust changes, run `just build-android` first.
- surprise/confusion point: Cargo config lookup is based on current working directory, not `--manifest-path`. Running `cargo check --manifest-path rust/Cargo.toml` from outside repo won't apply this repo's `.cargo/config.toml`.
- surprise/confusion point: Android `applicationIdSuffix` (dev flavor -> `org.bitcoinppl.cove.dev`) does not change Kotlin package/class names. `MainActivity` class is `org.bitcoinppl.cove.MainActivity`, so launcher scripts should resolve activity from package manager instead of assuming `<applicationId>.MainActivity`.
- surprise/confusion point: incremental APK packaging can leave huge ZIP gaps after native `.so` size shrinks (APK appears hundreds of MB larger than payload). Deleting prior `app/build/outputs/apk/dev/debug/app-dev-debug.apk` and `app/build/intermediates/apk/dev/debug/*.apk` before packaging fixes it.
- surprise/confusion point: built-in Arti SOCKS listener can accept TCP before Tor bootstrap is usable; early outbound SOCKS connects may fail with `general SOCKS server failure` even though the listener port is open. Treat this as transient at startup and retry briefly for built-in Tor flows.
- surprise/confusion point: Rust tracing logs were configured to stdout by default; on Android this often means Tor/Arti logs are not visible in logcat. Prefer stderr (or explicit Android logging integration) for Rust log visibility on device.
- surprise/confusion point: Android Network Settings "Connection Logs" UI originally used static placeholder strings (`TorUiState.logLines`) and was not wired to runtime Tor/Arti logs; it needs explicit log ingestion/polling to show real bootstrap activity.
- surprise/confusion point: `arti`/`arti-client` with `default-features = false` must explicitly enable `"onion-service-client"` for `.onion` destination streams. Without it, SOCKS connect attempts fail with `operation not supported because Arti feature disabled`.
- surprise/confusion point: custom-node parsing previously trusted the UI type label (`Custom Esplora` / `Custom Electrum`) over the URL scheme; a stale `Custom Esplora` label with `tcp://...:50001` produced `api_type=Esplora` + `Reqwest BadScheme`. Parse logic should infer/validate API type from URL hints too.
- surprise/confusion point: on Android, Arti config reload/watcher paths can emit XDG/HOME warnings (`Couldn't determine HOME directory`) even when runtime dirs are set for Tor client storage. For embedded built-in Tor mode, disable config watching unless live config reload is explicitly needed.
- surprise/confusion point: clearing Rust Tor log buffer when opening Network settings (`clearTorConnectionLogs()`) makes bootstrap progress appear stuck at 0 until a manual test; keep logs across screens and derive progress from ongoing Arti log stream.
- surprise/confusion point: if Tor is enabled with built-in mode, app startup previously did not warm up Arti until a node test/check path touched Tor; launch built-in Tor proactively at app start to avoid “looks idle until test” behavior.
- surprise/confusion point: Gradle configuration-cache occasionally fails on `:app:compileDevDebugKotlin` with `Failed to store cache entry ... Could not get file mode for ... .class`; rerun with `--no-configuration-cache` (or clean affected build intermediates) to verify code changes.
- surprise/confusion point: sharing port `127.0.0.1:9050` between built-in Arti and Orbot mode creates false-positive Orbot tests (checks hit lingering built-in listener). Keep built-in Tor on a dedicated SOCKS port (currently `39050`) and reserve `9050` for Orbot/external flows.
- surprise/confusion point: Android settings writes Tor mode as raw config strings (`GlobalConfigKey.TorMode` + `"BUILT_IN"/"ORBOT"/"EXTERNAL"`). Rust `TorMode` parsing must accept these uppercase forms; otherwise `config.tor_mode()` parse failure silently falls back to default (`BuiltIn`) and routes Orbot/External flows through built-in Tor.
- surprise/confusion point: quick-status bootstrap parsing should not treat every tor-related `[ERROR ...]` line as built-in Tor runtime failure; node-level connection errors (for example electrum retries during bootstrap) can otherwise turn the Tor status red prematurely.
- surprise/confusion point: for embedded Arti, avoid suppressing XDG/cache warnings at log-ingestion level; keep warnings visible in UI logs and instead treat known benign patterns as non-fatal in status parsing. This preserves debuggability when real path regressions return.
